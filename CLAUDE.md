# CommandZone — CLAUDE.md

## Architecture

### Routing

The app uses the Next.js App Router with two route groups:
- **Public routes** — `/`, `/login`, `/leaderboards`, `/player/[username]`, `/match/[id]`, `/collections/[id]`
- **Auth-required routes** — wrapped in `(main)/` group, enforced by `src/middleware.ts`

The `/` root is a dual-purpose dashboard — global view when logged out, personal view when logged in.

### Data Flow

1. **Server Components** fetch data via helpers in `src/lib/supabase/` using the server Supabase client.
2. **Server Actions** in `src/app/actions/` handle all mutations (create match, confirm, deck CRUD, etc.).
3. **Realtime** subscriptions (notifications, friend requests) are set up in hooks under `src/hooks/`.
4. **`jsonb` fields** (`match_data`, `participant_data`) are typed and validated at the data access boundary in `src/lib/supabase/` — components never receive untyped JSON.

### Supabase Clients

- `src/lib/supabase/server.ts` — server-side (Server Components, Server Actions, middleware)
- `src/lib/supabase/client.ts` — browser-side (hooks, client components only)

Always use `server-only` / `client-only` imports to prevent accidental misuse.

### Database Types

`src/types/database.types.ts` is auto-generated. Regenerate with:
```bash
npx supabase gen types typescript --linked > src/types/database.types.ts
```

Never hand-edit this file. All snake_case → camelCase mapping happens in `src/types/database-mappers.ts`.

## Rating System

The rating algorithm lives entirely in `src/lib/rating.ts` as pure functions — no side effects, fully unit-testable.

**Formula:** `Δ Rating = K × (Actual − Expected) × BracketModifier`

Key components:
- **Expected Score** — logistic ELO curve extended to N players: `player_factor / sum(all_factors)` where `factor = 10^(rating/400)`
- **K Factor** — 32 (0–20 matches), 24 (21–50), 16 (51+)
- **Bracket Modifier** — `1 + sign(gap) × |gap|^1.5 × 0.12` where `gap = avg_opponent_bracket − player_bracket`
- **Default bracket** — 2 (used when deck has no bracket set)

**Algorithm version** — `ALGORITHM_VERSION` constant in `rating.ts`. Increment when the formula changes; stored in `rating_history.algorithm_version` for audit trail.

**Rating scope** — Every confirmation updates two parallel tracks simultaneously:
- Global rating (per format)
- Collection-scoped rating (per format × collection, for every collection the match belongs to)

**Dirty match recalculation** — When a deck's bracket is updated post-confirmation, the match is flagged `is_dirty`. A nightly PL/pgSQL procedure `recalculate_dirty_matches()` re-runs affected ratings. The `pg_cron` job at 4am UTC is enabled (`024_enable_nightly_recalc_cron.sql`).

## Formats

Formats are config-driven in the `formats` DB table — new formats do not require code changes, just a new row (and, for team formats, `has_teams`/`win_condition_type`/`config`).

| Format | Players | Teams | Status |
|---|---|---|---|
| FFA | 3+ | No | Active |
| 1v1 | 2 | Yes | Active |
| Pentagram | 5 | Special (ally/enemy by seat position) | Active |
| 2-Headed Giant | 4 | Yes (2 teams of 2) | **Upcoming** — not yet built, will be a distinct format from `2v2` below |
| 2v2 | 4 | Yes | Sidelined (`is_active = false`) — kept in the schema, currently hidden from match creation, may return as its own format later |
| 3v3 | 6 | Yes | Sidelined (`is_active = false`) — same as 2v2 |

**Pentagram** — each player's two adjacent players are allies; their two non-adjacent players are enemies. All 5 players' ratings and brackets factor into expected score and bracket modifier calculations.

## Key Domain Concepts

**Placeholder participant** — A guest slot with no account. Can be retroactively claimed by a new user via the `/claim` flow. Owner approves/rejects via notification.

**Placeholder deck** — `"Unknown Deck"` sentinel. Any linked participant can retroactively update their slot to the real deck. Triggers dirty match recalculation if already confirmed.

**Confirmation model** — A player's rating only moves when *they* confirm a match. Reporter is auto-confirmed. Others confirm via notification. Matches can be partially confirmed.

**Rating history** — Append-only. Stores all algorithm inputs as snapshots (`player_bracket`, `opponent_avg_rating`, `opponent_avg_bracket`, `k_factor`, `algorithm_version`) enabling full retroactive recalculation.

**Collections** — Named groups of matches (pod, tournament, season, etc.). A match can belong to many collections. Match-add permissions: `owner_only`, `any_member`, `any_member_approval_required`.

## Agents

A GitHub agent config lives at `.github/agents/frontend-ui.agent.md`. It defines a frontend UI agent (Claude Opus 4.5) that verifies every change live in a browser via Chrome DevTools MCP.

**Agent workflow:** Understand → Plan → Edit → Verify in browser → Iterate → Confirm

**Agent boundaries:** Frontend files only (components, styles, assets). Does not touch backend, API, database, or config files unless explicitly asked.

## Code Conventions

- **TypeScript strict** — no `any`, no untyped `jsonb` crossing the data layer boundary
- **Tailwind CSS 4** — utility-first; design tokens defined in `globals.css`; use `tailwind-merge` (`cn()` util) for conditional classes
- **Prettier** — configured in `.prettierrc` with `prettier-plugin-tailwindcss` for class sorting
- **ESLint** — `eslint.config.mjs`, extends `next` + `prettier`
- **Server vs Client** — prefer Server Components by default; use `"use client"` only when interactivity or browser APIs are needed
- **Server Actions over API routes** — mutations go through `src/app/actions/`, not `/api/` (API routes reserved for debug/webhooks)
- **Pure functions for business logic** — rating algorithm and data transformations are pure and kept out of components
- **Error handling** — `src/lib/errors.ts` for typed errors; Sentry for production monitoring via `sentry.server.config.ts` / `sentry.edge.config.ts`
